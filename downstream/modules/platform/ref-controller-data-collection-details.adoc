= Details about data collected for {Analytics}

[role="_abstract"]
Metrics service exposes raw automation-controller data through enabled per-collector analytics API endpoints. This topic summarizes the data classes and collector modes; use Analytics API reference and the API data model for the authoritative endpoint and field contracts.


== Data collected

The enabled analytics collectors expose the following classes of data from
{ControllerName}:

* Basic configuration, such as which features are enabled, and what operating system is being used
* Topology and status of the {ControllerName} environment and hosts, including capacity and health
* Counts of automation resources:
  * organizations, teams, and users
  * inventories and hosts
  * credentials (indexed by type)
  * projects (indexed by type)
  * templates
  * schedules
  * active sessions
  * running and pending jobs
* Job execution details (start time, finish time, launch type, and success)
* Automation task details (success, host id, playbook/role, task name, and module used)

For field-level API schemas, use the discovery response, the metrics-service
API specification, and xref:con-understand-analytics-api-data-model-and-retention[Understand analytics API data model and retention].

== Collector types and scheduling

Metrics-service analytics uses three collector modes. The mode determines the
scheduled cadence and the default window used for on-demand collection.

=== Snapshot collectors

Capture point-in-time data representing current state, such as configuration
and topology. Snapshot collectors do not use a time window.

=== Daily collectors

Collect metrics that aggregate over a calendar day. Examples include
`main_host_daily`, `main_hostmetric`, and `main_indirectmanagednodeaudit`. An
on-demand request without explicit bounds uses the previous complete day.

=== Hourly collectors

Collect large tabular data sets including `events_table`,
`unified_jobs_dashboard`, and `workflow_job_node_table`. An on-demand request
without explicit bounds uses the previous complete hour.

== Collection processing and task timing

On-demand collection is asynchronous: the API returns `202 Accepted` with a
task URL, and the payload becomes available after the task completes. Response
and task timing depends on the collector, payload size, database, and system
load; the API does not define a processing-time SLA. See Analytics API
reference and xref:ref-analytics-api-error-handling-and-resilience[Analytics API error handling and resilience].

== Freshness reference

For API freshness, use the discovery and collection-envelope timing metadata
described in xref:proc-verify-analytics-data-freshness-using-timestamp-fields[Verify analytics data freshness using timestamp fields]. This topic
focuses on the data classes and collection behavior, not on repeating the API
freshness procedure.

== Collection failure and delay behavior

If an analytics collection task fails or is delayed, no successful collection
envelope is created for that task. Understanding this behavior helps you
interpret gaps in API data.

=== Data gap semantics

A failed scheduled task can leave a gap in stored collection envelopes. A later
collection does not implicitly rewrite or deduplicate earlier envelopes; use an
explicit on-demand window when a targeted retry is needed.

=== No collection-status or backfill-status endpoint

No public API endpoint exposes collection run status or backfill state. Use the
task status and collection-envelope timing metadata (see Verify analytics data
freshness using timestamp fields) to confirm collection completion.
