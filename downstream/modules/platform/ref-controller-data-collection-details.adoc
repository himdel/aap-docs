= Details about data collected for {Analytics}

[role="_abstract"]
{ControllerNameStart} collects configuration, topology, job execution, and task details and sends them to Red Hat when {Analytics} is enabled. This topic describes the collected data classes, collector types, timestamp fields for data-currency verification, and collection failure behavior.


== Data collected

{Analytics} collects the following classes of data from {ControllerName}:

* Basic configuration, such as which features are enabled, and what operating system is being used
* Topology and status of the {ControllerName} environment and hosts, including capacity and health
* Counts of automation resources:
  * organizations, teams, and users
  * inventories and hosts
  * credentials (indexed by type)
  * projects (indexed by type)
  * templates
  * schedules
  * active sessions
  * running and pending jobs
* Job execution details (start time, finish time, launch type, and success)
* Automation task details (success, host id, playbook/role, task name, and module used)

You can use `awx-manage gather_analytics` (without `--ship`) to inspect the data that {ControllerName} sends, so that you can satisfy your data collection concerns. This creates a .tar file that contains the analytics data that is sent to Red Hat.

For field-level schema definitions of each file in the tar archive, see the link:https://access.redhat.com/articles/7124201[xref:assembly-using-data-dictionary[{Analytics} Data Dictionary]].

== Collector types and scheduling

{Analytics} uses three collector classifications. The classification determines how frequently each data type is collected and how it affects data freshness.

=== Snapshot collectors

Capture point-in-time data representing current state, such as configuration
and topology. Snapshot collectors run at each collection window trigger. Use
the discovery `last_collect` and collection-envelope timing fields to verify
API freshness.

=== Daily collectors

Collect metrics that aggregate over a calendar day. Examples include
`main_host_daily`, `main_hostmetric`, and `main_indirectmanagednodeaudit`. Use
the collection envelope's `finished_at` to verify API freshness; payload fields
are collector-specific.

=== Hourly collectors (CSV, high-cost)

Collect large tabular data sets including `events_table`,
`unified_jobs_dashboard`, and `workflow_job_node_table` using the hourly
collection window. Because of their size, these collectors are the primary
driver of collection processing time at large event volumes.

For the collection lag formula and how system load affects processing time, see xref:ref-controller-analytics-gathering[Analytics gathering].

== Collection processing time

After an upstream collection window opens, {ControllerName} gathers,
packages, and ships {Analytics} data. The time required for this
processing depends on the volume of job events accumulated since the previous
collection. These processing figures describe the upstream shipping path; use
the metrics-service collection envelope timing for API freshness.

The following table shows observed processing times by event volume tier. These figures are from internal performance testing and represent observed behavior, not a service level agreement (SLA).

[options="header"]
|===
|Approximate event volume |Observed processing time
|\~1,000 events |\~11 seconds
|\~10,000 events |11–18 seconds
|\~100,000 events |\~33 seconds
|===

For the complete lag formula (collection window wait + processing time), see xref:ref-controller-analytics-gathering[Analytics gathering].

== Freshness reference

For API freshness, use the discovery and collection-envelope timing metadata
described in xref:proc-verify-analytics-data-freshness-using-timestamp-fields[Verify analytics data freshness using timestamp fields]. This topic
focuses on the data collected and the behavior of the upstream shipping path,
not on repeating the API freshness procedure.

== Collection failure and delay behavior

If an upstream analytics collection cycle fails or is delayed, the data for
that window is not collected. Understanding these failure semantics helps you
interpret gaps in {Analytics} data.

=== Data gap semantics

A missed collection cycle creates a gap in analytics data for that window's time period. {ControllerNameStart} does not automatically backfill the gap when the next successful collection runs. The next successful collection covers only events that fall within the new collection window.

=== No collection-status or backfill-status endpoint

No public API endpoint exposes collection run status or backfill state. Use
the discovery and collection-envelope timing metadata (see Verify analytics
data freshness using timestamp fields) to confirm collection cycle completion.

=== Recovery

For recovery actions, including the manual gather command, see Manage
analytics and data collection in {PlatformNameShort} and Analytics
gathering. For API freshness verification, see Verify analytics data freshness
using timestamp fields.
