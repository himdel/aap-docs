= Verify analytics data freshness using timestamp fields

[role="_abstract"]
You can verify whether {Analytics} data is current by checking the discovery endpoint's last_collect value and the collection timing fields. Payload timestamp fields provide additional validation when available.


.Prerequisites

* {Analytics} is enabled in {ControllerName} settings.
* You know the time recorded in the `AUTOMATION_ANALYTICS_LAST_GATHER` controller setting, or the scheduled collection window close time. For how to locate this setting and collection window timing, see xref:ref-controller-analytics-gathering[Analytics gathering].
* You have API access to the {Analytics} endpoint on the Red Hat Hybrid Cloud Console.

.Context

Upstream {Analytics} shipping introduces a lag between job completion
and data availability through that shipping path. The lag can include the
four-hour shipping window and collection processing time. Metrics-service API
requests use the stored collection envelope timing instead. For background on
both paths, see xref:ref-controller-analytics-gathering[Analytics gathering].

The discovery endpoint reports last_collect for each collector. Each collection record also includes started_at and finished_at. Compare these values with the expected collection window to identify stale data.

.Procedure

. Identify the collector and its collection timing metadata.

   Use the discovery entry's `last_collect` and the collection envelope's
   `started_at`/`finished_at`. Payload timestamp fields are optional,
   collector-specific validation:


[options="header"]
|===
|Data |Primary freshness signal |Collector type
|Any API collector |Discovery `last_collect`, or envelope `finished_at` |Snapshot, daily, or hourly
|Job event payloads |`modified` and `job_created` when payload-level validation is useful |`controller.events_table`
|Host payloads |Collector-specific fields such as `created`, `modified`, or `last_automation` |Daily or snapshot collectors
|===



. Check the collector's latest collection metadata.

   Use the discovery endpoint to check last_collect. You can also request the collector rows and inspect the first result, which is the newest collection record.

   *Examples:*

   For *Job Events*, query the newest collection envelope and inspect its
   `finished_at`; inspect `modified` or `job_created` inside `payload` when
   payload-level validation is needed:

[source,sh]
----
curl -H "Authorization: Bearer <your-token>" \
  "https://<gateway-hostname>/api/metrics/v1/analytics/controller.events_table/?page=1&page_size=1"
----

   For *System Data* (Daily collector), query the discovery entry or the
   newest `main_host_daily` collection envelope:

[source,sh]
----
curl -H "Authorization: Bearer <your-token>" \
  "https://<gateway-hostname>/api/metrics/v1/analytics/controller.main_host_daily/?page=1&page_size=1"
----

   For *Cluster Data* (Snapshot collector), use the discovery entry and the
   newest collection envelope. Snapshot payload fields are collector-specific;
   the current API registry does not define a universal cluster-state payload
   or common `timestamp` field:

[source,sh]
----
curl -H "Authorization: Bearer <your-token>" \
  "https://<gateway-hostname>/api/metrics/v1/analytics/<snapshot-collector>/?page=1&page_size=1"
----

   Replace `<your-token>` with an authentication token created in {ControllerName}, and `<gateway-hostname>` with your {ControllerName} hostname. For how to create a token, see xref:ref-analytics-api-reference[Analytics API reference].



. Compare the returned collection timing metadata against the expected window close time.

   The expected collection close time depends on the collector mode and its
   configured schedule. Compare `finished_at`/`last_collect` with that expected
   close time; do not infer freshness from a fixed payload field shared by all
   collectors.

   For processing time estimates by event volume, see xref:ref-controller-analytics-gathering[Analytics gathering].

. Evaluate the collection timing comparison and take the appropriate action.

   * If `finished_at` or `last_collect` is at or after the expected window close time, the collection cycle completed successfully and data is current.
   * If the collection timing predates the expected window close time, the collection cycle has not yet completed. Wait for the current collection window to finish, or trigger collection manually.

.Result

The collection timing comparison tells you whether the most recent collection cycle has completed. If data is current, `finished_at` or `last_collect` is at or after the expected collection window close time. If data is stale, use the recovery steps in the post-requisite section.

.Post-requisites

If data appears stale after the collection window has closed, the collection cycle may have failed or been delayed. To trigger an immediate collection, run the following command:

[source,sh]
----
$ awx-manage gather_analytics --ship
----

For full recovery procedures including connectivity checks, see xref:proc-manage-analytics-and-data-collection-in-ansible-automation-platform[xref:proc-manage-analytics-and-data-collection-in-ansible-automation-platform[Manage analytics and data collection] in {PlatformNameShort}].

For collection failure behavior and data gap semantics, see xref:ref-controller-data-collection-details[Details about data collected for {Analytics}].
