= {Analytics} Data Dictionary

[role="_abstract"]
This data dictionary describes the JSON contract exposed by the metrics-service analytics API. It covers discovery metadata, stored collection envelopes, on-demand collection responses, and the raw payload fields for each enabled collector.


== Overview

The analytics API stores each successful gather as a collection envelope. The envelope identifies the collector, source, {ControllerNameStart} installation, collection window, and gather timing; its `payload` contains the collector-specific JSON output. The OpenAPI schema is the source for the field types and nullability represented in the tables below.

The original {Analytics} dictionary used numbered sections and field-level tables with field name, type, example, and description columns. This draft keeps that field-by-field approach but uses API-contract columns: `Required` distinguishes omission from `Nullable`, and nested paths show where array items and dynamic object values occur. Examples are intentionally omitted when the OpenAPI contract does not define one.

== API responses covered

[options="header"]
|===
|Operation |Status |Data described
|`GET /api/v1/analytics/` |`200` |Discovery response and enabled collector metadata.
|`GET /api/v1/analytics/{collector}/` |`200` |Paginated collection envelopes and collector payloads.
|`POST /api/v1/analytics/{collector}/collect/` |`200` |Existing completed task reused for the requested window.
|`POST /api/v1/analytics/{collector}/collect/` |`202` |Collection task created, requeued, or still in flight.
|`POST /api/v1/analytics/{collector}/collect/` |`409` |Different collection window already in flight.
|===

== Shared discovery response

`GET /api/v1/analytics/` returns a `200` response containing a `collectors` array. The `key_field` value is null for arrays and fixed-key objects; for keyed objects it identifies what the top-level object keys represent.

[options="header"]
|===
|Field |Type |Required |Nullable |Description
|`name` |string |No |No |
|`description` |string |No |No |
|`payload_shape` |string (`object`, `array`) |No |No |Top-level JSON shape of payload: object or array. * `object` - object * `array` - array
|`key_field` |string |No |Yes |Field represented by top-level object keys, or null when not applicable.
|`mode` |string |No |No |
|`accepts_since_until` |boolean |No |No |
|`last_collect` |date-time |No |Yes |
|`rows_url` |string |No |No |
|`collect_url` |string |No |No |
|===

== Shared collection response

`GET /api/v1/analytics/{collector}/` returns a `200` paginated response. `count` counts stored collection envelopes, not records inside a payload. Each result has the following shared envelope fields; the collector-specific `payload` fields are documented below.

[options="header"]
|===
|Field |Type |Required |Nullable |Description
|`count` |integer |Yes |No |
|`next` |string |Yes |Yes |
|`previous` |string |Yes |Yes |
|`results` |array of one of the documented collector payload shapes |Yes |No |
|===

=== Collection envelope fields

[options="header"]
|===
|Field |Type |Required |Nullable |Description
|`id` |integer |No |No |Unique stored collection envelope identifier.
|`collector` |string |No |No |Public `group.function` collector name; it selects the payload schema.
|`source` |string |No |No |Originating platform component, normally `local`.
|`cluster_id` |string |No |Yes |{ControllerNameStart} installation UUID (`INSTALL_UUID`), or null if unavailable.
|`since` |date-time |No |Yes |Inclusive start bound passed to the collector; null for snapshots or open bounds.
|`until` |date-time |No |Yes |Exclusive end bound passed to the collector; null for snapshots or open bounds.
|`started_at` |date-time |No |No |Timestamp when collection started.
|`finished_at` |date-time |No |No |Timestamp when collection finished.
|`payload` |collector-specific JSON |Yes |No |Raw JSON output from the collector before rollup preparation.
|===

`Required` reflects the OpenAPI schema's required-property list. The response-only envelope serializers emit the read-only metadata fields, including `id`, on stored rows even when those fields are not listed as required by the generated component. The envelope `id` identifies the stored collection row; it is distinct from any `id` inside a collector payload.

== On-demand collection request and responses

`POST /api/v1/analytics/{collector}/collect/` accepts the following optional JSON fields. Omitted bounds use the mode-specific default; snapshot collectors reject bounds.

[options="header"]
|===
|Field |Type |Required |Nullable |Description
|`since` |date-time |No |Yes |Collection start; omitted values use the mode default.
|`until` |date-time |No |Yes |Collection end; omitted values use the mode default.
|===

The `200` and `202` response bodies have the same fields. The status indicates whether the resolved task is already completed (`200`) or work is created, requeued, or still in flight (`202`).

[options="header"]
|===
|Field |Type |Required |Nullable |Description
|`task_id` |integer |Yes |No |
|`task_url` |string |Yes |No |
|`collector` |string |Yes |No |
|`task_data` |object |Yes |No |
|`task_status` |string |Yes |No |Current Task status.
|`disposition` |string (`created`, `reused`, `requeued`) |Yes |No |Whether this request created a task, reused an existing one, or requeued a failed/stale one. * `created` - created * `reused` - reused * `requeued` - requeued
|===

A `409` response means another pending or running task covers a different window for the same collector:

[options="header"]
|===
|Field |Type |Required |Nullable |Description
|`detail` |string |Yes |No |
|`task_id` |integer |Yes |No |
|`task_url` |string |Yes |No |
|`task_status` |string |Yes |No |
|`task_data` |object |Yes |No |
|===
