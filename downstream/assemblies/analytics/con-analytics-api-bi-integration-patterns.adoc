= Analytics API BI integration patterns

[role="_abstract"]
Business intelligence (BI) tools can integrate with the {PlatformNameShort} analytics API using documented trigger patterns, customer-side join queries, and real-world workflow scenarios. This topic provides prescriptive guidance for BI architects and data engineers.


== Prerequisites

* You have System Administrator or System Auditor role access to {ControllerName}.
* Your {ControllerName} deployment is running AAP 2.7 or later.
* You have a BI tool or REST client that supports JSON API data sources.

== Recommended trigger patterns for BI connectors

The analytics API supports two documented trigger patterns for data collection: manual POST and scheduled POST. Choose the pattern that fits your BI tool's capabilities and refresh schedule.

=== Pattern 1: Manual POST to /collect/ endpoint

Use this pattern when your BI tool supports triggering external API calls before running a refresh.

*When to use:*

* Your BI refresh job can execute a pre-refresh webhook or HTTP request.
* You want to guarantee fresh data before every BI query.
* You need to trigger collection on demand (for example, after a major automation run completes).

*How it works:*

. Your BI tool's pre-refresh script sends a POST request to the collector endpoint:

[source,sh]
----
curl -X POST \
  -H "Authorization: Bearer <your-token>" \
  https://<gateway-hostname>/api/metrics/v1/analytics/controller.events_table/collect/
----

. The analytics API queues a background task and returns `202 Accepted` with
   `task_id` and `task_url`. The request does not wait for collection to finish.

. Poll or otherwise monitor the task URL until the collection completes.

. Your BI tool queries the GET endpoint to retrieve the fresh collection envelope:

[source,sh]
----
curl -H "Authorization: Bearer <your-token>" \
  "https://<gateway-hostname>/api/metrics/v1/analytics/controller.events_table/?page=1&page_size=100"
----

IMPORTANT: Wait for collection to complete before querying data. Allow at least 1–2 minutes between the POST trigger and the GET query to account for collection processing time. For expected processing times by event volume, see Understand analytics API architecture and performance.

*Task behavior:* Repeating a POST for the same collector and resolved window
reuses the existing background task. Requests for different windows of the same
collector can receive `409 Conflict` while another window is running. Use the
returned `task_url` and `task_id` to monitor the task before querying the data.

=== Pattern 2: Metrics-service recurring task

Use this pattern when your BI tool cannot trigger external API calls but the
metrics-service scheduler can own the collection schedule.

*When to use:*

* Your BI tool supports only GET requests (no pre-refresh webhook capability).
* You want to align collection timing with BI refresh schedules without embedding trigger logic in the BI tool.
* You prefer server-side collection scheduling managed by metrics service.

*How it works:*

. Create a recurring task in metrics service. For example, an hourly task for
   the `events_table` collector uses the metrics-service task API:

[source,sh]
----
curl -X POST \
  -H "Authorization: Bearer <your-token>" \
  -H "Content-Type: application/json" \
  -d '{
      "name": "Analytics collection for BI tool",
      "function_name": "collect_hourly_metrics",
      "task_data": {"collector_type": "events_table"},
      "cron_expression": "0 * * * *"
    }' \
  https://<gateway-hostname>/api/metrics/v1/tasks/schedule_recurring/
----

. Metrics service creates a child collection task on each cron fire.

. Your BI tool queries the analytics GET endpoint after the task completes to retrieve fresh data. Creating the recurring task requires a System Administrator; a System Auditor can use the resulting schedule and read its reports but cannot create or remove the schedule.

Use `collect_daily_metrics` with a daily collector or `collect_snapshot_metrics`
with a snapshot collector. See xref:ref-analytics-api-reference[Analytics API reference] for the collector modes
and default windows.

=== Pattern 3: GET-based collection trigger (not supported)

*Do not use this pattern in production.* Querying an empty collector endpoint
does not automatically trigger collection. Use Pattern 1 or Pattern 2 instead.

Use Pattern 1 (manual POST) or Pattern 2 (scheduled POST) instead.

== Customer-side data preparation

The API returns separate collector feeds rather than pre-joined datasets. Retrieve the feeds you need, inspect the fields returned for each collector, and perform joins or aggregations in your BI tool. Use the discovery response and the metrics-service API specification to confirm available fields and join keys.

== Real-world workflow scenarios

The following scenarios address common BI integration challenges and provide prescriptive guidance for handling them.

=== Scenario 1: First-time full extraction (initial load)

*Goal:* Load all available historical data from the analytics API into your BI tool for the first time.

*Workflow:*

. If you need the current default window, trigger collection for the collectors
   you need:

[source,sh]
----
curl -X POST -H "Authorization: Bearer <token>" \
  https://<gateway-hostname>/api/metrics/v1/analytics/controller.events_table/collect/
curl -X POST -H "Authorization: Bearer <token>" \
  https://<gateway-hostname>/api/metrics/v1/analytics/controller.unified_jobs_dashboard/collect/
----

   An on-demand POST without bounds collects only the previous complete hour
   or day, depending on the collector mode; it does not backfill the full
   retention period. An unbounded GET reads historical collections that are
   already stored.

. Wait 1–2 minutes for collection to complete.

. Query each collector without `since` or `until` filters to retrieve all available data:

[source,sh]
----
curl -H "Authorization: Bearer <token>" \
  "https://<gateway-hostname>/api/metrics/v1/analytics/controller.events_table/?page=1&page_size=100"
----

. Page through collection envelopes using the `next` URL in the response until `next` is null. Flatten each envelope's `payload` before loading its event or job records into the BI tool.

. Store the retrieved data in your BI tool database.

. Record the collection IDs or collection windows already loaded. Do not use
   the maximum timestamp of a nested record as a row-level delta cursor: `since`
   and `until` select overlapping stored collection windows.

*Expected performance:* For a full-retention window with \~100,000 events, expect 2.8–3.5 seconds per page of collection envelopes and their nested payloads. A complete extraction may take several minutes depending on data volume.

=== Scenario 2: Incremental refresh pattern (daily delta loads)

*Goal:* Update BI data without treating timestamp filters as row-level deltas.

Stored collections can contain records that overlap a requested window. Track the collection IDs or windows already processed, request the relevant windows, and deduplicate records in the BI database before merging new data. Do not assume that `since` set to the last record timestamp returns only new data.

=== Scenario 3: Token expiry during refresh (error handling and recovery)

*Goal:* Gracefully handle authentication token expiry during a long-running BI refresh.

*Workflow:*

. Before starting refresh, check token validity:

[source,sh]
----
curl -I -H "Authorization: Bearer <token>" \
  https://<gateway-hostname>/api/metrics/v1/analytics/
----

. If you receive a 401 Unauthorized response, create a new token in {ControllerName}.

. Update your BI tool configuration with the new token.

. Retry the failed query.

*Prevention:* Rotate tokens on a regular schedule (for example, every 90 days) rather than waiting for expiry. For token rotation instructions, see xref:ref-analytics-api-reference[Analytics API reference].

=== Scenario 4: Retention window changes (impact on historical data)

*Goal:* Understand how retention window changes affect available historical data.

*Scenario:* Your analytics API retention period changes from 90 days to 30 days.

*Impact:*

* Data older than 30 days is purged from the analytics API.
* Your next full extraction retrieves only 30 days of history.
* Historical data beyond 30 days is lost unless you previously stored it in your BI tool database.

*Mitigation:*

* Pull analytics data frequently (daily or every few hours) and store it in your BI tool database.
* Do not rely on the analytics API for long-term historical storage.
* Monitor the effective retention from the {ControllerNameStart} `cleanup_jobs` schedule.

=== Scenario 5: Timezone and DST date handling

*Goal:* Correctly filter data by date ranges when your BI tool and {ControllerName} are in different timezones.

*Best practice:*

* Always use ISO 8601 timestamps in UTC for `since` and `until` parameters:

[source,sh]
----
?since=2026-10-01T00:00:00Z&until=2026-10-31T23:59:59Z
----

* Convert BI tool local times to UTC before constructing the API query.

* Store timestamps in UTC in your BI tool database to avoid DST ambiguity.

*Example:* Querying for October 2026 data in New York (EDT, UTC-4):

* Local start: `2026-10-01 00:00:00 EDT` → UTC: `2026-10-01T04:00:00Z`
* Local end: `2026-10-31 23:59:59 EDT` → UTC: `2026-11-01T03:59:59Z`

Use the UTC values in the API query.

== Performance expectations for common queries

The following performance characteristics help you set realistic expectations for BI refresh jobs and dashboard load times.

*Typical 30-day query:*

* 1,000 rows: \~287ms (p50)
* 10,000 rows: \~534ms (p50)

*Full-retention query (\~100,000 events):*

* Collection time: \~30 seconds
* First readable response: \~33 seconds
* Repeated reads of 61–65 MB: 2.8–3.5 seconds (p50)

*Large dataset extraction:*

* 102,762 real controller events = 61 MB response, 2.80 seconds read time (p50)

NOTE: Response latency includes Gateway authentication, database lookup, JSON serialization, network transfer, and client parsing. These figures represent observed behavior, not service level agreement (SLA) guarantees.

*Recommendation:* Set customer expectations that this is reporting data (not transactional). Slower response times are acceptable for large historical queries.

== Role-based access control and auditor limitations

The analytics API enforces role-based access control (RBAC) based on your {ControllerName} user role.

=== System Administrator role

* *GET permission:* Yes (read all collectors)
* *POST permission:* Yes (trigger collection cycles)

*Use case:* BI administrators who need to trigger collections on demand.

=== System Auditor role

* *GET permission:* Yes (read all collectors)
* *POST permission:* No (403 Forbidden on POST to /collect/)

*Use case:* Read-only BI users who query analytics data but cannot modify collection schedules or trigger collections.

IMPORTANT: If a System Auditor user or BI service account attempts to POST to a `/collect/` endpoint, the API returns a 403 Forbidden response. Ensure your BI tool uses a System Administrator account if it needs to trigger collections, or use Pattern 2 (scheduled POST) with an admin-created recurring task.

=== Organization-scoped roles

Organization-scoped roles do not have analytics API access. See Analytics API
reference for the authoritative RBAC matrix.

== Troubleshooting common integration errors

=== Error: 403 Forbidden on POST to /collect/

*Cause:* Your BI tool is using a System Auditor token or an organization-scoped user token.

*Solution:*

. Verify the token belongs to a System Administrator account.
. If using a System Auditor account, switch to Pattern 2 (scheduled POST) where an admin creates the recurring task.
. If using an organization-scoped account, create a new token for a System Administrator user.

=== Error: 401 Unauthorized

*Cause:* Token is invalid, expired, or deleted.

*Solution:*

. Verify the token exists in {ControllerName} (*Access* > *Users* > *Tokens*).
. Create a new token if the old one was deleted.
. Update your BI tool configuration with the new token.

=== Error: Empty result set despite recent job activity

*Cause:* Collection has not run since the job completed, or you queried too soon after triggering collection.

*Solution:*

. Wait 1–2 minutes after POSTing to `/collect/` before querying data.
. Verify collection completed using the collection timing metadata. For
   instructions, see xref:proc-verify-analytics-data-freshness-using-timestamp-fields[Verify analytics data freshness using timestamp fields].
. If the collection timing is stale, manually trigger collection with POST
   to `/collect/`.

=== Error: Data older than expected is missing

*Cause:* Data aged out of the configured retention window (with a 90-day fallback; shorter for Managed Cloud or indirect-node data).

*Solution:*

. Verify the effective retention period from the {ControllerNameStart} `cleanup_jobs`
   schedule, as described in xref:con-understand-analytics-api-data-model-and-retention[Understand analytics API data model and retention].
. Pull data more frequently (daily or every few hours) to avoid losing historical data.
. Store long-term historical data in your BI tool database, not the analytics API.

=== Error: One page does not contain all payload data

*Cause:* `page_size` caps the number of collection envelopes returned; the
event or job records are nested inside each envelope's `payload`.

*Solution:*

. Use the `next` URL in the response to retrieve additional collection pages,
   then flatten each page's `payload`:

[source,json]
----
{
  "count": 2,
  "next": "https://<gateway-hostname>/api/metrics/v1/analytics/controller.events_table/?page=2&page_size=100",
  "results": [{"collector": "controller.events_table", "payload": [...]}]
}
----

. Iterate through pages until `next` is null.
