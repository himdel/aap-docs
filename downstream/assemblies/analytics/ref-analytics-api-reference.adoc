= Analytics API reference

[role="_abstract"]
The analytics API provides programmatic access to {ControllerName} analytics data through per-collector HTTP endpoints. Use this API to integrate {PlatformNameShort} analytics into external business intelligence (BI) tools such as Grafana, Power BI, Tableau, or ELK.


== Prerequisites

* {Analytics} is enabled in {ControllerName} settings. For configuration instructions, see xref:proc-controller-configure-analytics[Configure {Analytics}].
* You have System Administrator or System Auditor role access to {ControllerName}.
* Your {ControllerName} deployment is running AAP 2.7 or later.

== API base URL

The analytics API is available at the following base URL:

[source]
----
https://<gateway-hostname>/api/metrics/v1/analytics/
----

Replace `<gateway-hostname>` with your {ControllerName} hostname or IP address.

== Authentication

The analytics API uses token-based authentication via the {ControllerName} Gateway. No certificate-based authentication (mTLS) is required or supported.

=== Creating an authentication token

. From the navigation panel in {ControllerName}, select *Access* > *Users*.
. Select your user account.
. Select the *Tokens* tab.
. Click *Add*.
. Select *Read* scope for read-only access (System Auditor), or *Write* scope for triggering collections (System Administrator).
. Click *Save*.
. Copy the generated token. You cannot retrieve the token value after closing the dialog.

=== Using the token

Include the token in the `Authorization` header of every API request:

[source,sh]
----
curl -H "Authorization: Bearer <your-token>" \
  https://<gateway-hostname>/api/metrics/v1/analytics/<collector-name>/
----

=== Token rotation and revocation

Tokens do not expire automatically. To rotate a token:

. Create a new token following the steps above.
. Update your BI tool configuration to use the new token.
. Delete the old token from the *Tokens* tab.

To revoke a token immediately, delete it from the *Tokens* tab. All API requests using that token will fail with a 401 Unauthorized response.

== RBAC and role limitations

The analytics API enforces role-based access control (RBAC) based on your {ControllerName} user role:

[options="header"]
|===
|Role |GET (read) permission |POST (trigger collection) permission
|System Administrator |Yes |Yes
|System Auditor |Yes |No (403 Forbidden)
|Organization Admin |No |No
|Organization Auditor |No |No
|===

IMPORTANT: Only System Administrator and System Auditor roles can access the analytics API. Organization-scoped roles do not have analytics API access.

System Auditor users can query analytics data but cannot trigger collection cycles. If a System Auditor attempts to POST to a collection endpoint, the API returns a 403 Forbidden response.

== Per-collector endpoints

The analytics API exposes one endpoint per collector. Each collector represents a distinct data table from {ControllerName}.

=== Endpoint pattern

[source]
----
GET /api/metrics/v1/analytics/<collector-name>/
POST /api/metrics/v1/analytics/<collector-name>/collect/
----

* *GET* retrieves collected data for the specified collector.
* *POST* triggers a new data collection cycle (System Administrator only).

=== Available collectors

The discovery endpoint is the authoritative source for enabled collectors in this deployment. It returns each collector's name, description, data shape, mode, window support, last_collect, and the URLs for reading and triggering collection.

The current AAP 2.7 registry contains 28 enabled collectors: 10 hourly, 15 snapshot, and 3 daily. For detailed field schemas, see the xref:assembly-using-data-dictionary[{Analytics} Data Dictionary].

== Query parameters

=== Filtering by collection window

Use since and until to filter collection windows that overlap the requested interval:

[source,sh]
----
GET /api/metrics/v1/analytics/controller.unified_jobs_dashboard/?since=2026-10-01T00:00:00Z&until=2026-10-14T23:59:59Z
----

* *since*: Inclusive lower bound for the collection window.
* *until*: Exclusive upper bound for the collection window.
* These parameters filter collection windows, not individual records inside their payloads. Omitting both returns all stored data within the retention window.

=== Pagination

The API paginates collections. Use page and page_size. The count value counts collections, not records inside their payloads:

[source,sh]
----
GET /api/metrics/v1/analytics/controller.events_table/?page=1&page_size=100
----

* *page*: Page number within the result set.
* *page_size*: Number of collections to return per page.

The response includes next and previous URLs for navigating paginated collections. Each result includes the collector, collection window, collection timing, and its data.

[source,json]
----
{
  "count": 2,
  "next": "https://<gateway-hostname>/api/metrics/v1/analytics/controller.events_table/?page=2&page_size=100",
  "previous": null,
  "results": [{"id": 123, "collector": "controller.events_table", "started_at": "...", "finished_at": "...", "payload": [...]}]
}
----

=== Collection metadata

The discovery endpoint reports last_collect for each collector. Each collection record includes started_at and finished_at. A POST to /collect/ returns task_id and task_url. The API does not provide a separate collection-status or backfill-status endpoint.

== Triggering data collection

System Administrators can queue an on-demand collection task by POSTing to a collector's `/collect/` endpoint. Each request returns HTTP 202 Accepted with a task_id and task_url:

[source,sh]
----
curl -X POST \
  -H "Authorization: Bearer <your-token>" \
  https://<gateway-hostname>/api/metrics/v1/analytics/controller.events_table/collect/
----

=== Trigger mechanisms

Analytics data collection can be triggered three ways:

. *Manual POST*: Explicitly POST to `/collect/` as shown above. Available to System Administrators only.
. *Scheduled service tasks*: Metrics service runs collection tasks according to the configured hourly, daily, and snapshot schedules. No user intervention is required.
. *Per-collector defaults*: Each collector type has a default collection frequency (hourly, daily, or snapshot). The scheduler triggers collections based on these defaults.

NOTE: GET-based auto-trigger (automatic collection when querying an endpoint) is not a supported mechanism in AAP 2.7. Manual POST and scheduled cron are the only documented trigger methods.

=== Collection windows and timing

When `since` and `until` are omitted from an on-demand POST, the API applies
mode-specific defaults:

* *Hourly collectors*: The previous complete hour.
* *Daily collectors*: The previous complete day.
* *Snapshot collectors*: No time window (point-in-time capture).

These defaults apply to the queued API task; they do not backfill the full
retention period. To request a different window, include explicit `since` and
`until` values in the POST body.

For collection lag and processing time details, see xref:con-understand-analytics-api-architecture-and-performance[Understand analytics API architecture and performance].

== Security model and data exposure

The analytics API exposes a defined allowlist of {ControllerName} data. Understanding what is and is not exposed is critical for security review and compliance.

=== Data included in the analytics API

The following data classes are available through the analytics API:

* Job execution metadata (job ID, start time, finish time, status, launch type)
* Task execution details, including task and action fields, host information, and success status
* Host and inventory counts (total hosts, active hosts, organization attribution)
* Resource counts (organizations, teams, users, credentials, projects, templates)
* Cluster topology and configuration (node count, capacity, health status)
* Playbook and role names (no content or task details)
* Hostnames and IP addresses (customer domain data)
* Indirect node audit records (indirect node counts, organization attribution, collection timestamps)

=== Data excluded from the analytics API

The following sensitive data is *not* exposed through the analytics API:

* Playbook file content
* Task stdout or stderr output
* Credential values (passwords, tokens, API keys, SSH keys)
* Secret fields from custom credential types
* Module arguments containing sensitive data
* `extra_vars` values
* Vault-encrypted data
* User email addresses and personal identifiable information (where applicable)

=== Shared responsibility model

*Red Hat responsibility:*

* Enforce RBAC at the API gateway
* Provide token rotation and revocation mechanisms
* Limit data exposure to the defined allowlist
* Secure data in transit (HTTPS only)

*Customer responsibility:*

* Secure authentication tokens (store in secrets manager, rotate regularly)
* Control access to BI tools that consume analytics data
* Apply appropriate data retention policies in BI systems
* Secure analytics data at rest in BI tool databases
* Monitor and audit BI tool access logs

IMPORTANT: Once analytics data is pulled from the API into your BI tool, securing that copy is your responsibility. The analytics API provides the data; you control how it is stored, accessed, and retained in your BI environment.
