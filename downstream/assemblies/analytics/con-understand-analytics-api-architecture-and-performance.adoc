= Understand analytics API architecture and performance

[role="_abstract"]
The analytics API serves {ControllerName} data from isolated storage that does not compete with operational workloads. Understanding the architecture, performance characteristics, and data freshness timing helps you set realistic expectations and configure effective BI tool refresh schedules.


== Production isolation

Analytics queries do not affect running automation jobs. The analytics API reads from isolated storage that is decoupled from the operational {ControllerName} database.

*How isolation works:*

. {ControllerNameStart} collects analytics data on a scheduled interval (default: 4 hours).
. The metrics service processes and stores collected data in a dedicated analytics database.
. BI tools query the analytics API, which reads from the dedicated analytics database.
. Operational job execution continues unaffected by analytics queries.

*What this means for BI integration:*

* You can run complex, long-running queries against the analytics API without impacting job execution performance.
* Analytics data is batch-collected, not real-time. Expect lag between job completion and data availability.
* High-volume BI queries do not compete for database resources with active automation workloads.

== Data freshness and collection lag

Analytics data is not real-time. The observable lag between job completion and data availability in the analytics API is the sum of two stages:

=== Stage 1: Collection window wait

The time from job completion until the next scheduled collection window triggers. For the default 4-hour collection interval, this wait can be up to 4 hours.

*Example:*

* Job completes at 02:15.
* Next collection window opens at 04:00.
* Collection window wait: 1 hour 45 minutes.

=== Stage 2: Collection processing time

The time required to gather, package, and ship analytics data after the collection window opens. Processing time varies with the volume of job events accumulated since the previous collection.

*Observed processing times by event volume:*

[options="header"]
|===
|Approximate event volume |Observed processing time
|\~100 events |\~11 seconds
|\~1,000 events |\~11 seconds
|\~10,000 events |11–18 seconds
|\~100,000 events |\~33 seconds
|===

NOTE: These figures are from internal performance testing and represent observed behavior, not a service level agreement (SLA). System load on the {ControllerName} host can increase processing time beyond these figures.

=== Total observable lag

Total lag = collection window wait + collection processing time.

*Example with default 4-hour window:*

* Job completes at 02:15.
* Next collection window opens at 04:00 (1h 45m wait).
* 10,000 events accumulated since last collection.
* Processing time: \~18 seconds.
* Total lag: \~1h 45m 18s.

Data becomes queryable in the analytics API at approximately 04:00:18.

*Recommendation for BI refresh scheduling:* Schedule BI tool refresh to run at least *1–2 minutes after the collection window closes* to account for processing time and avoid querying incomplete data.

== Access methods

The analytics API uses HTTPS with Gateway token authentication. No other access method is required or supported.

*Supported:*

* HTTPS REST API calls with `Authorization: Bearer <token>` header.

*Not supported:*

* SSH access to the metrics service database.
* Direct database queries (SQL access to the analytics database).
* CLI tools for triggering collection (use the API's POST `/collect` endpoint or the `awx-manage gather_analytics` command in {ControllerName}).
* Cron job configuration for collection triggers (collection scheduling is managed automatically by {ControllerName}).

IMPORTANT: Do not attempt to access the analytics database directly via SQL. The analytics API is the only supported interface for retrieving analytics data.

== Performance characteristics

Performance characteristics help you set realistic expectations for BI tool response times and determine appropriate query patterns.

=== Collection performance

Collection performance measures the time from POST to `/collect` to data becoming readable in the analytics API:

[options="header"]
|===
|Event volume |Collection time
|\~100 events |\~11 seconds
|\~1,000 events |\~11 seconds
|\~10,000 events |11–18 seconds
|\~100,000 events |\~33 seconds
|===

These figures include gathering data from {ControllerName}, processing, and persisting to the analytics database.

=== BI response latency

BI response latency measures the time from API request to receiving data (for already-collected data):

[options="header"]
|===
|Record count |Response latency (p50)
|100 rows |\~200 ms
|1,000 rows |\~290 ms
|10,000 rows |\~530 ms
|100,000 rows |\~3.3 seconds
|===

*Real-world example:*

* 102,762 job events from a production controller.
* Response size: \~61 MB JSON.
* Response time: \~2.8 seconds (p50).

NOTE: Response latency includes Gateway authentication, database lookup, JSON serialization, network transfer, and client parsing. The analytics API does not provide SLA guarantees for response times.

=== Recommended query patterns

Based on observed performance characteristics:

. *Use pagination for large result sets*: Request 1,000–10,000 records per page, not 100,000 at once. This keeps response times under 1 second.

. *Filter by time range*: Use `since` and `until` parameters to limit results to the time range you need. Requesting 90 days of data when you need only today's data wastes bandwidth and processing time.

. *Pull data frequently*: Pull data daily or every few hours rather than once per week. This keeps each query small and fast.

. *Avoid complex server-side joins*: The API serves raw per-collector feeds. Perform joins in your BI tool, not by requesting multiple collectors in a single API call.

== Collector type scheduling

Analytics uses three collector classifications that affect how frequently each data type is refreshed:

=== Snapshot collectors

Capture point-in-time cluster state. Run at each collection window trigger (default: every 4 hours).

*Example collector:* `controller.cluster_info`

*Refresh frequency:* Every 4 hours (default).

=== Daily collectors

Collect metrics that aggregate over a calendar day. Run once per collection window.

*Example collectors:*

* `controller.main_host_daily` (host activity aggregates)
* `controller.main_hostmetric` (host performance metrics)
* `controller.main_indirectmanagednodeaudit` (indirect node audit records)

*Refresh frequency:* Every 4 hours (default), but data represents daily aggregates.

=== Hourly collectors (CSV, high-cost)

Collect large tabular data sets using 4-hour time slicing. Primary driver of collection processing time at high event volumes.

*Example collectors:*

* `controller.events_table` (job events and task execution)
* `controller.unified_jobs_table` (job execution records)
* `controller.workflow_job_node_table` (workflow job nodes)

*Refresh frequency:* Every 4 hours (default), with 4-hour time slicing to bound result set size.

NOTE: Despite the "hourly" classification name, these collectors use 4-hour time windows. The "hourly" label refers to the collector run frequency relative to other collector types, not the data refresh interval. The effective data refresh interval matches the collection window (4 hours by default).

== Deployment-specific considerations

The analytics API is available in all {PlatformNameShort} deployment types, but some deployment-specific constraints apply.

=== Containerized (RHEL 9)

Full analytics API access with no deployment-specific constraints. Retention period follows the controller retention setting or defaults to 90 days.

=== {OCPShort} (Operator)

Full analytics API access with no deployment-specific constraints. Retention period follows the controller retention setting or defaults to 90 days.

=== Managed Cloud

Managed Cloud deployments may have *shorter retention periods* than self-managed deployments due to storage constraints and multi-tenant architecture.

*Recommendation for Managed Cloud users:*

* Contact Red Hat Support to confirm the retention period for your Managed Cloud environment.
* Pull analytics data more frequently (daily or every few hours) to avoid losing historical data to rolling-window purges.
* Store long-term historical data in your BI tool database, not the analytics API.
